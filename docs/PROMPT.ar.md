# 2OneByte-Coder — البرومبت الرئيسي للبناء (ترجمة عربية)

> انسخ المستند كله وحطه في وكيل برمجة (Claude Code أو مشابه) جوه ريبو فاضي اسمه `2OneByte-Coder`. كل اللي تحت مواصفات. ابني على المراحل المذكورة في القسم 20، اعمل commit بعد كل مرحلة، وماتتخطاش فحوصات القبول.

---

## 1. الدور والهدف

أنت مهندس رئيسي (principal engineer) ومصمم منتجات. ابني **2OneByte-Coder**: منشئ تطبيقات بالذكاء الاصطناعي، احترافي، عربي أولًا (RTL)، بيشتغل كـ **APK أندرويد** (وكمان كـ PWA / نسخة ويب من نفس الكود).

المستخدم بيوصف مشروعه. فريق موديلات ذكاء اصطناعي متخصصة، كل واحد له وظيفة واحدة بس، بيخطط له، ويكتب الكود **لايف على الشاشة**، ويعرضه، ويراجعه بصريًا، ويصلحه، ويفحصه أمنيًا، وفي الآخر ينشره على GitHub (ريبو، README، ملف بناء، وGitHub Pages للمواقع).

مستوى الجودة: المنتجات اللي بتتولد والتطبيق نفسه لازم يبقوا زي البرامج الاحترافية، مش نموذج أولي. كل قرار في الواجهة لازم يتبرر باسم عنصر دقيق من قاموس NameThatUI البصري (القسم 4).

## 2. قواعد صارمة

1. ماتخترعش إصدارات مكتبات أو حقول API أو endpoints من الذاكرة. دوّر عليها (سجل الحزم، المستندات الرسمية) وقت البناء ووقت التوليد.
2. ماتخزنش أسرار (مفاتيح API، توكنات GitHub) في الكود أو اللوجات أو الريبو أو لقطات الشاشة أو المشاريع المتولدة. استخدم تخزين الجهاز المشفر بس.
3. ماتنشرش مشروع فاشل في بوابة الجودة (القسم 13، الخطوة 3). بلّغ بالعوائق بدل النشر.
4. كل وكيل وظيفة واحدة، وبياخد السياق اللي محتاجه بس. ماحدش بيعدل ملفات برا اختصاصه.
5. كل العمليات الطويلة قابلة للإلغاء والاستكمال وبتعرض تقدم.
6. الواجهة RTL عربي افتراضيًا مع دعم إنجليزي كامل. الكود وأسماء الملفات والـ identifiers تفضل LTR.
7. حد أدنى لإمكانية الوصول: WCAG 2.2 AA (تباين، focus-visible، مساحات لمس 44px على الأقل، احترام reduced-motion).

## 3. القرارات التقنية

- **غلاف التطبيق:** TypeScript وReact وVite وTailwind CSS مع design tokens وRadix UI وFramer Motion (spring easing). يتغلف لأندرويد بـ Capacitor. نفس الكود بيشتغل كـ PWA.
- **المحرر:** CodeMirror 6 (خفيف على الموبايل) مع تلوين الصيغة لكل اللغات المدعومة، وعرض افتراضي (virtualised)، ووضع "كتابة لايف" بيضيف توكنات الموديل أول بأول وهي بتيجي.
- **معاينة التيرمنال:** xterm.js. بايثون بيشتغل جوه المتصفح بـ Pyodide، وJavaScript في worker معزول، واللغات التانية عن طريق runner بعيد اختياري (القسم 11).
- **التخزين:** IndexedDB للمشاريع والملفات والتاريخ وطابور التعديلات (عبر Dexie). طبقة نظام ملفات افتراضي (`VFS`) بتوحّد الاستيراد والتصدير والـ zip. الأسرار في المخزن الآمن للمنصة (Android Keystore عبر plugin تخزين آمن لـ Capacitor).
- **الحالة:** store واحد مبني على الأحداث (event-sourced)؛ كل فعل من أي وكيل هو حدث، فالتشغيل ممكن يتعاد ويتكمل ويتراجع.
- **الوصول للموديلات:** عميل واحد مش مرتبط بمزود معين، بيتكلم بروتوكول chat completions المتوافق مع OpenAI مع الـ streaming (SSE) واستدعاء الأدوات وإعادة المحاولة مع backoff وtimeout لكل طلب. المزودين بيضبطهم المستخدم (القسم 6).
- **CI / النشر:** GitHub REST API مع workflows لـ GitHub Actions بتتولد حسب نوع المشروع (القسم 13).

## 4. نظام التصميم ومرجع NameThatUI

موقع NameThatUI (https://namethatui.com) هو "قاموس بصري للواجهات": لكل عنصر اسم حقيقي، ورمز API في كل إطار عمل، وتشريح (anatomy)، وملاحظة "بيتلخبط مع إيه"، و**برومبت جاهز للصق** لوكلاء البرمجة. فيه جزء تاني (`/styles` واسمه "Name That Vibe") بيفهرس الأساليب البصرية (Glassmorphism، Neobrutalism، Minimalism، Flat Design، Neumorphism، Claymorphism، Skeuomorphism، Liquid Glass، Frutiger Aero، Aqua، Windows Aero، Y2K، Web Brutalism، Vernacular Web)، ولكل أسلوب علامات مميزة وbrief.

### 4.1 أداة `ui-reference` (إجبارية لكل وكيل بيكتب واجهات)

نفّذ أداة لازم الوكلاء يستدعوها قبل كتابة أي كود واجهة:

- `ui_lookup(description)` ← بتجيب صفحات المصطلحات المطابقة من namethatui.com (روابط المصطلحات بالشكل `https://namethatui.com/web/<slug>` و`https://namethatui.com/macos/<slug>`، والأساليب في `/styles/<slug>`)، وتستخرج: الاسم الحقيقي، جدول رموز الـ API، التشريح، عناصر "بيتلخبط مع"، البرومبت الجاهز، وبرومبت التشخيص (debug).
- خزّن النتائج على الجهاز بمدة صلاحية 7 أيام، وهات صفحات قليلة بس في كل تشغيل، وعرّف التطبيق بـ User-Agent واضح، واعرض دايمًا نسب الفضل ("قاموس الواجهات: NameThatUI") في شاشة "عن التطبيق". ماتعملش سحب جماعي للموقع.
- الوكيل لازم يذكر المصطلحات اللي استخدمها في ملف `design-notes.md` جوه كل مشروع متولد (مثلًا: "Header vs Navigation Bar"، "Bento Grid"، "Toast (Snackbar)"، "Command Palette"، "Skeleton vs Spinner"، "Empty State").

## 6. الإعدادات

بتتفتح من قائمة الهامبرجر على **اليمين**.

### 6.1 مزود الموديل (كارت واحد، أربع خانات)

- `Name` و`Provider` و`Base URL` و`API key`.
- زرار **List models** ← بينادي `GET {baseUrl}/models` ويفتح Data Table:
  - الأعمدة: معرّف الموديل، سعر الدخل، سعر الخرج، نافذة السياق (context)، أقصى توكنات خرج، **Status Dot** (أخضر = طلب فحص صغير رجّع HTTP 200، أحمر = كود تاني ويظهر الكود، رمادي = لسه ماتفحصش)؛
  - السعر والسياق وحدود التوكنات بتتقرأ من رد المزود لو موجودة (مزودين كتير بيعرضوا الأسعار و`context_length`)؛ لو مش موجودة اعرض شرطة، ومتخمنش أبدًا؛
  - الفلاتر: بحث نصي، "اللي بيرد 200 بس"، مجاني / مدفوع، حد أدنى للسياق، وترتيب بأي عمود؛
  - إجراء "Test" بيشغّل الفحص (طلب chat completion بتوكن واحد) لكل موديل أو لكل الصفوف الظاهرة بحد أقصى للتوازي وإمكانية إلغاء؛
  - المستخدم يقدر يميّز الموديلات بنجمة ويعيّنها للأدوار (القسم 8).
- خانة API key مقنّعة ومخزنة في المخزن الآمن ومابتتسجلش أبدًا، وفي الكارت "Test connection".
- يدعم أكتر من كارت مزود؛ واحد منهم افتراضي.

### 6.2 GitHub

- كارت للصق **توكن GitHub** (يفضل fine-grained personal access token). اعرض الصلاحيات المطلوبة بالظبط: Contents (قراءة وكتابة)، Metadata (قراءة)، Administration (كتابة، لإنشاء الريبوهات)، Pages (كتابة)، Actions (قراءة وكتابة)، Workflows (كتابة). التوكنات الكلاسيكية محتاجة `repo` و`workflow`.
- "Verify token" بينادي `GET /user` ويعرض الصلاحيات الممنوحة؛ اعرض الصلاحية الناقصة بدل ما الفشل يظهر بعدين.
- قسم **Plugins**: مفاتيح تشغيل للقدرات (قراءة ريبو، كتابة ملفات، إنشاء ريبو، تفعيل Pages، تشغيل وقراءة Actions، إنشاء releases) عشان المستخدم يشوف التطبيق مسموح له بإيه.

## 7. الشاشة الرئيسية

- شبكة **كروت** مشاريع. كل كارت: اسم المشروع، اللغة الأساسية (نص)، عدد الملفات، وعلى **الشمال** (الطرف البعيد في الشاشة RTL) أيقونة اللغة (Python، JavaScript، TypeScript، Dart/Flutter، Kotlin، Java، C#، Go، Rust، C/C++، PHP، HTML/CSS، Shell…). وفّر مجموعة أيقونات مع أيقونة بديلة عامة.
- أعلى اليمين: زرار **"+"** وجنبه **"مشروع جديد"**.
- نافذة **مشروع جديد**:
  1. الاسم، والوصف (متعدد الأسطر وكبير).
  2. الاستيراد (اختياري): سحب وإفلات أو اختيار أي سكريبت/ملف، أو ملف **.zip**؛ أو اختيار "ابدأ من الصفر".
  3. عند التأكيد، **الـ Planner** (القسم 8) بيقرا الوصف ويحلله بالكامل ويطلّع الخطة التفصيلية (القسم 10)، وبعدها تفتح مساحة العمل والخطة ظاهرة والكود بيبدأ ينزل.
- في المشروع الجديد كليًا بتفتح مساحة العمل على الوصف؛ وفي المشروع المستورد بتفتح على شجرة الملفات مع ملخص التحليل.

## 8. الوكلاء (كل واحد متخصص)

كل الوكلاء بيتضبطوا بالدور في الإعدادات؛ الدور الواحد ممكن يستخدم أي موديل من أي مزود. الأدوار:

1. **الـ Planner (الموديل الأساسي).** بيفهم الوصف؛ بيختار نوع المشروع (website, apk, cli, exe, library) واللغات والـ frameworks وقاعدة البيانات وأحدث إصدارات المكتبات (متحقق منها عبر سجلات الحزم) وعدد الملفات وهيكلها؛ ويكتب الخطة الرئيسية وجرد الدوال.
2. **الـ Coder.** بيكتب ويعدّل ملفات الكود بس. بيتختار من شريط Workspace الجانبي ("موديل الكود"). مالوش رأي في التخطيط أو المراجعة.
3. **الـ Runner/Observer.** بيشغّل المعاينة ويلتقط لقطات شاشة ومقاييس DOM وأخطاء الـ console واللوجات. كود حتمي (deterministic) مع موديل بيشوف الصور للحكم.
4. **الـ Visual Critic.** بيقارن اللي شافه بالوصف وبملاحظات التصميم؛ ويسرد كل عيب مع العنصر والملف ودرجة الخطورة.
5. **الـ Fixer.** بياخد قائمة العيوب المجمّعة، ويفتح الملفات المعنية بس، ويصلحها.
6. **الـ Expert (المراجع / الأمان).** بيتختار وقت النشر ("اختار موديل للفحص"). مراجعة الكود، التنظيف، فحص الثغرات، README.
7. **الـ Release engineer.** كود حتمي (مش موديل) بيتكلم مع GitHub.

لكل وكيل system prompt وقائمة أدوات مسموحة وميزانية توكنات ومخطط JSON للخرج بيتحقق منه قبل الاستخدام. الخرج غير الصالح بيتعاد مع أخطاء التحقق لحد حد أقصى للمحاولات.

## 9. نظام المهارات (`skills.md`)

المهارات ملفات markdown بـ front-matter:

```md
---
name: web-visual-polish
description: Refine layout, colour, spacing and motion of websites
applies_to: [website, apk]
triggers: [landing page, dashboard, portfolio, store, UI, design]
always: false
---
# Instructions
...
```

- الإعدادات ← **المهارات**: عرض، بحث، فلترة حسب `applies_to`، إضافة، تعديل، تفعيل/تعطيل، واستيراد/تصدير `skills.md`.
- **موجّه المهارات (Skill router):** بياخد وصف المشروع ونوعه ويختار المهارات المناسبة (درجة كلمات مفتاحية مع نداء موديل صغير للتأكيد) ويحقنها في الوكلاء الصح. مهارات `always: true` بتتحقن دايمًا.
- **مهارات مدمجة إجبارية (اشحن دول على الأقل، مكتوبين بالكامل):**
  - `requirements-understanding` (دايمًا): من وصف نصي حر، تحدد عدد الملفات المطلوب، وأنسب لغة لكل جزء، وأنسب قاعدة بيانات، وأحدث مكتبات مستقرة لكل لغة (متحقق منها بالبحث)، وهيكل المجلدات، والبيئات، والاختبارات، والأسئلة المفتوحة. لازم تطلّع مبرر لكل اختيار.
  - `ui-reference-namethatui` (دايمًا للـ website/apk): إزاي ومتى تنادي `ui_lookup`، وإزاي تختار أسلوب من `/styles`، وإزاي تكتب `design-notes.md`.
  - `web-frontend-pro` و`web-backend-pro` و`mobile-app-pro` و`cli-pro` و`desktop-app-pro`.
  - `visual-qa` و`code-quality` و`security-audit` و`testing` و`git-and-release` و`readme-writer` و`accessibility` و`performance`.
  - `arabic-rtl` (عكس التخطيط، الخطوط، الأرقام، النص ثنائي الاتجاه).
- المستخدم يقدر يكتب مهارات خاصة به؛ ومحرر المهارات بيعرض أي مشاريع/وكلاء هتطابق المهارة حاليًا.

## 10. مخرجات التخطيط (اللي لازم الـ Planner يطلّعه)

خطة JSON متحقق منها مع `PLAN.md` مقروء للبشر:

- ملخص المشروع والمستخدمين المستهدفين.
- نوع المشروع وهدف التشغيل (website / apk / cli / exe).
- اختيارات الـ stack مع الأسباب والإصدارات المتحقق منها.
- **قائمة الملفات** كاملة مع غرض كل ملف.
- **جرد الدوال والكلاسات** كامل: لكل ملف، كل دالة مع التوقيع (signature) والمدخلات والمخرجات والأخطاء، والدوال التانية اللي بتناديها.
- نموذج البيانات وعقد الـ API (لو موجود).
- قائمة الشاشات وخريطة التنقل (لمشاريع الواجهات) بأسماء عناصر NameThatUI.
- ملخص التصميم: الأسلوب المختار، اللوحة، الخطوط، سلم المسافات، قواعد الحركة.
- خطة الاختبار ومعايير القبول مكتوبة كفحوصات يقدر الـ Observer يتحقق منها.
- المخاطر والافتراضات.

الخطة بتتعرض للمستخدم كـ Outline View قابل للطي، وممكن يعدّلها قبل ما الكود يبدأ. توليد الكود بيمشي ورا الخطة ملف ملف؛ أي انحراف لازم يحدّث الخطة.

## 11. مساحة العمل

### 11.1 التخطيط

- **أعلى اليسار:** زرار Sidebar. بيفتح لوحة فيها:
  - اختيار **موديل الكود** (موديل بيكتب الملفات بس)؛
  - زرار **Preview**؛
  - كارت **الملفات** وتحته **شجرة الملفات** (Outline View، أيقونة لغة لكل ملف، مثلًا `main.py` مع أيقونة Python، مجلدات قابلة للطي، عدد الملفات، علامات التعديل)؛
  - تحت كارت الملفات، زرار **النشر على GitHub** (القسم 13).
- **المنتصف:** محرر الكود. الملفات اللي الـ Coder بيكتبها بتتظلل لايف؛ المستخدم بيشوف التوكنات بتظهر في الملف الصح، مع وضع "متابعة" بيسكرول للسطر النشط وزرار إيقاف مؤقت/استكمال. الفروقات (diffs) للتعديلات بتتعرض داخل المحرر (سطور مضافة/محذوفة).
- **تحت:** شريط كتابة بسطر واحد بيتوسع. المستخدم يكتب تعديل إضافي (مثلًا "ضيف قايمة فيها كذا وكذا وكذا") ويدوس إرسال. الرسائل بتروح **طابور التعديلات** (القسم 12).

### 11.2 أوضاع المعاينة

- **Website:** iframe معزول (sandboxed) بيتغذى من الـ VFS عبر service worker؛ hot reload عند تغيّر الملف؛ تبديل حجم الجهاز.
- **APK / تطبيق موبايل:** إطار موبايل مع عرض **Runtime**. لمشاريع React Native / Flutter-web / Capacitor اعرض نسخة الويب داخل الإطار؛ للمشاريع native بس اعرض نسخة ويب مرسومة للشاشات اللي في الخطة. وضّح بصراحة مستوى الدقة المعروض.
- **CLI:** تيرمنال xterm.js؛ بايثون عبر Pyodide وJS عبر worker؛ واللغات التانية عبر الـ remote runner (خدمة Docker صغيرة المستخدم يقدر يستضيفها بنفسه؛ التطبيق بيشتغل من غيرها ويقول أنهي لغات محتاجاها).
- **Desktop (exe):** معاينة كواجهة ويب مع مخرجات التيرمنال لطبقة المنطق.

## 12. حلقة المراجعة البصرية (الميزة الأساسية)

1. المستخدم يدوس **Preview**. الـ Observer بيشغّل المشروع ويسجّل، لمدة حوالي دقيقتين افتراضيًا، لقطات لكل شاشة/حالة، ومخرجات الـ console، وأخطاء الشبكة، ومقاييس الـ DOM (تداخل، أزرار لازقة أو متداخلة، نص مقصوص، تباين ضعيف، غياب focus styles، مسافات غير متسقة، محاذاة غلط في RTL).
2. لما تنتهي نافذة المراقبة، اعرض **Popover** فيه زرارين:
   - **كمّل مشاهدة (دقيقتين كمان)** — بيمدّد المراقبة؛ ولما الوقت يخلص الـ popover بيظهر تاني.
   - **ابدأ تعديل آخر** — بيبدأ دورة الإصلاح.
3. دورة الإصلاح:
   - الـ Visual Critic بيقارن اللي شافه بالوصف وبملاحظات التصميم، و**بيجمّع كل المشاكل مرة واحدة** (مثلًا: زرارين لازقين في بعض، ألوان ضعيفة، عدم تناسق، بنية غير احترافية)؛
   - بيحدد الملفات والعناصر المعنية بالظبط؛
   - الـ Fixer بيفتح الملفات دي ويصلح كل حاجة في تمريرة واحدة؛
   - بعدها بيشتغل تحليل كامل للكود (lint، فحص أنواع، اختبارات، كود ميت، imports غير مستخدمة) لحد ما يبقى نضيف؛
   - المعاينة بتتعاد والـ Observer بيكرر المراجعة.
4. بعد أول دورة إصلاح مكتملة، الـ popover بيضيف زرار تالت **"كدا تمام"** بيقبل الحالة الحالية. الزرارين التانيين بيفضلوا موجودين.
5. المستخدم يقدر كمان يكتب نقده الخاص في شريط الكتابة ("الألوان مش حلوة، مفيش تناسق، مش احترافي")؛ والـ Visual Critic بيدمجه مع ملاحظاته قبل الإصلاح.
6. شروط الإيقاف لتجنب الحلقات اللانهائية: حد أقصى لعدد الدورات لكل طلب (افتراضي 5)؛ ولو عدد المشاكل ماقلّش دورتين ورا بعض، وقّف وبلّغ.

## 13. النشر على GitHub (تحت كارت الملفات)

الزرار: **النشر على GitHub**. المسار:

1. **نقل للخبير.** بتظهر قائمة صغيرة فيها **اختار موديل للفحص**؛ المستخدم بيختار أي موديل من المزود المضبوط (غالبًا غير موديل الـ Coder).
2. الـ Expert بيشتغل بالترتيب:
   - مراجعة الكود وتنظيفه (تنسيق، بنية، تسمية، كود ميت، تعليقات حيث تفيد)؛
   - تشغيل الاختبارات وإصلاحها؛
   - **فحص أمني:** تحليل ثابت، فحص الأسرار، فحص التبعيات (حزم معروفة بثغرات)، فحوصات injection/XSS/SSRF/path traversal/unsafe deserialisation، مراجعة صلاحيات Android manifest، وCORS/CSP للمواقع؛
   - توليد README (إيه هو، لقطات شاشة، التثبيت، التشغيل، البناء، الإعداد، الرخصة).
3. **بوابة الجودة:** الـ Expert بيقيّم المشروع من 0 لـ 10 على معيار منشور (الصحة، الأمان، البنية، الاختبارات، التوثيق، جودة الواجهة، إمكانية الوصول، الأداء، التبعيات، الجاهزية للإصدار). النشر بيكمل عند **10/10** بس. غير كده، حلقة (إصلاح ثم إعادة فحص) لحد حد أقصى؛ ولو ماوصلش 10/10 اعرض العوائق المتبقية وماتنشرش.
4. بعدها الـ Release engineer:
   - بينشئ الريبو (خاص افتراضيًا، والمستخدم يقدر يختار عام)، ويعمل commits برسائل مفيدة؛
   - بيضيف ملف `.github/workflows` حسب نوع المشروع: **apk** (بناء Gradle أو Flutter أو Capacitor، ملف debug أو release موقّع، مرفق في GitHub Release)، **exe** (Windows runner مع PyInstaller / Electron Builder / Tauri)، **website** (بناء ثم نشر على GitHub Pages، وتفعيل Pages عبر الـ API)، **cli** (تجميع وإرفاق binaries أو نشر حزمة)؛
   - بيستنى الـ workflow ويقرا نتيجة التشغيل ويعيد مرة واحدة لو الفشل مؤقت.
5. زرار **التفاصيل** بيظهر **بعد** نجاح النشر بس ويعرض: رابط الموقع (للمواقع)، رابط الريبو، رابط ملف البناء، الإصدار، تقرير التقييم، وإجراء نسخ الرابط.
6. التعديلات بعد كده ممكنة؛ المستخدم يقدر ينشر تاني وبيتعمل إصدار جديد.

## 14. طابور التعديلات

- كل رسالة من شريط الكتابة بتبقى عنصر في الطابور بحالة: في الانتظار، شغّال، تم، فشل، ملغي.
- العناصر بتشتغل واحد واحد بالترتيب؛ والطابور بيفضل بعد إعادة تشغيل التطبيق.
- إجراءات: إعادة ترتيب، تعديل، إلغاء، و"شغّل دلوقتي"؛ وكل عنصر بيسجّل الملفات اللي لمسها ويقدر يتراجع عنه (لقطة لكل عنصر).
- التعارضات: عنصرين بيلمسوا نفس المنطقة بيتدمجوا بواسطة الـ Planner قبل التشغيل.

## 15. الاستيراد

- يقبل أي ملف نصي أو سكريبت، وملفات `.zip`. فك الضغط داخل الـ VFS، واكتشاف اللغات ونقاط الدخول والتبعيات، وعرض ملخص التحليل، وخلّي الـ Planner يبني خطة من الكود الموجود قبل أي تغيير.
- حماية من zip bombs وpath traversal (`..`)، وفرض حدود للحجم، وتخطي الملفات الثنائية إلا لو لازمة، وماتنفذش كود مستورد برا الـ sandbox أبدًا.

## 16. معالجة الأخطاء، العمل بدون إنترنت، الأداء

- رسائل خطأ واضحة ومترجمة مع إجراء استرداد. حدود المعدل (HTTP 429) بتتعامل معاها بـ backoff تلقائي.
- لو الشبكة وقعت، الطابور بيتوقف ويكمل.
- المشاريع الكبيرة: تحميل كسول للملفات، شجرة virtualised، دفعات streaming عبر requestAnimationFrame، وبدون تهنيج على أجهزة أندرويد متوسطة.

## 17. أمان التطبيق نفسه

- تخزين آمن للأسرار؛ خيار قفل بالبصمة.
- Content Security Policy؛ والـ iframe بتاع المعاينة معزول (مفيش وصول لتخزين التطبيق أو التوكنات).
- الكود المتولد مابياخدش مفاتيح المستخدم أبدًا؛ والـ Expert والـ Coder بياخدوا الملفات اللي محتاجينها بس.
- نظافة ضد prompt-injection: النص داخل الملفات المستوردة أو الصفحات المجلوبة هو بيانات، مش تعليمات أبدًا؛ واستدعاءات الأدوات من الوكلاء بتتحقق ضد قوائم مسموح بها.
- ملفات lock للتبعيات، و`npm audit` في الـ CI، وإعداد Dependabot.

## 18. الاختبارات
